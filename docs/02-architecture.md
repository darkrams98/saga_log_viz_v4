# ۲ — معماری: یک کار، و همان را خوب

> این سند نسخهٔ فعلی را توصیف می‌کند: **نمایش یک لاگ**.
> برای تاریخچهٔ اینکه چرا از ELK به MongoDB آمدیم، [۱ — تحلیل](01-analysis.md) را ببینید.

---

## تقسیم کار با ابزارهای موجود

مهم‌ترین تصمیم معماری این نسخه، کاری است که **انجام نمی‌دهد**:

| نیاز | ابزار |
|---|---|
| پایش کلی، نمودار، هشدار | **Grafana** |
| جستجوی گسترده، پیدا کردن شناسه | **ELK / Elasticsearch** |
| فهمیدن *یک* فرایند مشخص | **این سرویس** |

پشتیبان با ELK شناسه را پیدا می‌کند و آن را اینجا می‌چسباند. همین.
هیچ داشبوردی، هیچ فهرست لاگی، هیچ نمودار زمانی. این محدودیت، نه کمبود،
بلکه دلیل سبک و سریع بودن سرویس است.

---

## جریان داده

```
                    شناسه (از ELK)
                          │
                          ▼
          ┌──────────────────────────────┐
          │  find({ _id: ... })          │  ← دقیقاً یک پرس‌وجو
          └──────────────────────────────┘
                          │  سند خام در حافظه
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
   FlowGraphBuilder  DocumentFlattener  MaskingService
     (گراف جریان)     (نمای جدولی)      (JSON خام)
          └───────────────┼───────────────┘
                          ▼
                  یک پاسخ JSON واحد
                          ▼
              داشبورد فارسی/RTL — سه زبانه
```

**هر سه نما از همان یک سند ساخته می‌شوند.** هیچ lookup، هیچ aggregate،
هیچ پرس‌وجوی دوم. این ادعا در پاسخ API قابل بررسی است:

```json
{ "mongoOperations": 1, "operations": ["findOne"] }
```

## دو حالت جستجو، عمداً جدا

### عادی — سریع و همیشه امن

```
GET /api/v1/log/{id}
```

فقط روی فیلدی که در `config.json` هم `enabled` است و هم `indexed`.
پیش‌فرض `_id` است که MongoDB خودش رویش ایندکس یکتا دارد.

اگر کسی فیلد دیگری بخواهد، سرویس با یک پیام صریح رد می‌کند:

> جستجو روی «registerId» در حالت عادی مجاز نیست، چون این فیلد در
> config.json به‌عنوان فیلد ایندکس‌شده معرفی نشده است.

و در راه‌اندازی، `IndexInspector` ادعای `indexed: true` را با `listIndexes`
راستی‌آزمایی می‌کند. اگر کسی فیلدی را فعال کند ولی ایندکسش را نساخته باشد،
هشدار در لاگ و در `/meta/health` ظاهر می‌شود — پیش از آنکه پشتیبان با یک
کوئری چندثانیه‌ای غافلگیر شود.

### پیشرفته — گران، و صادقانه گران

```
POST /api/v1/log/advanced   { "filters": [ {field, op, value}, … ] }
```

فیلترهای پویا روی هر فیلدی، حتی بدون ایندکس. سه محافظ دارد:

1. **سقف تعداد** (پیش‌فرض ۲۰)
2. **سقف زمان اجرا** روی خود MongoDB (`maxTimeMS`)
3. **بدون `sort`** — این یکی از بقیه مهم‌تر است. مرتب‌سازی یا کل نتیجه را
   در حافظه می‌ریزد (و با «Sort exceeded memory limit» می‌افتد) یا سرور را
   وادار می‌کند تا آخر اسکن کند. بدون sort، MongoDB به‌محض یافتن ۲۰ سند
   متوقف می‌شود. UI هم همین را می‌گوید: «نتایج به ترتیب زمانی نیستند».

خروجی‌اش هم عمداً یک **فهرست کوتاه برای انتخاب** است، نه جدولی برای مرور:
هدف رسیدن به یک شناسه است، نه پایش.

`POST` بودن هم تصمیم است، نه سلیقه: این عملیات نباید سهواً از نوار آدرس،
bookmark یا prefetch مرورگر اجرا شود.

## گراف جریان اجرا

هستهٔ نمایشی این نسخه. از `commandList` ساخته می‌شود:

- **هر گره** = یک میکروسرویس (`routingKey` → برچسب فارسی از config)
- **هر یال** = ترتیب اجرا در آرایه
- **رنگ** = از `statusSeverity` در config: سبز / قرمز / خاکستری
- **شروع و پایان** = دو نشانگر، تا مرز فرایند معلوم باشد
- **کلیک روی گره** = `title`، `commandType`، `commandContent`، `response`

چیدمان **افقی راست‌به‌چپ** است، هم‌راستا با خود رابط: نگاه کاربر فارسی‌زبان
از راست شروع می‌شود، پس «درخواست کاربر» هم آنجاست.

### چرا SVG دستی و نه یک کتابخانهٔ گراف؟

- جریان ما یک **زنجیرهٔ خطی** است، نه گراف دلخواه. یک کتابخانهٔ layout
  (dagre / elk / cytoscape) صدها کیلوبایت اضافه می‌کرد برای مسئله‌ای که
  چند سطر حساب مختصات است.
- کنترل کامل روی جهت RTL و فونت فارسی.
- **هیچ وابستگی خارجی یعنی هیچ CDNی لازم نیست** — که در شبکهٔ بستهٔ بانک
  اهمیت دارد.

### چیزی که در عمل گرفتار شدیم

در SVG، معنای `text-anchor: start/end` به **جهت متن** وابسته است. چون صفحه
RTL است، `end` لبهٔ چپ می‌شود نه راست، و متن از جعبه بیرون می‌زند.
تنها لنگر مستقل از جهت `middle` است. همهٔ برچسب‌های گره با همان چیده شده‌اند.

## قراردادهایی که نباید شکسته شوند

### ۱) هیچ مسیری استثنا پرتاب نمی‌کند

`FlowGraphBuilder.build()` و `LogLookupService.present()` هرگز پرتاب
نمی‌کنند. بدترین حالت، گراف خالی با یک توضیح فارسی است:

> فیلد «commandList» آرایه نیست (string)؛ گراف قابل رسم نیست، ولی نمای
> جدولی و JSON خام کامل‌اند.

جملهٔ دوم مهم است: کاربر باید بداند کجا هنوز می‌تواند داده را ببیند.

### ۲) هیچ برچسبی «نامشخص» نمی‌شود

اگر ترجمه‌ای در config نبود، **مقدار خام** نمایش داده می‌شود. پشتیبانی که
`orchestration26.new.service.routing.key` را می‌بیند دست‌کم می‌تواند در ELK
دنبالش بگردد؛ کسی که «نامشخص» می‌بیند نه.

### ۳) وضعیت ناشناخته «موفق» فرض نمی‌شود

`statusSeverity` فقط وضعیت‌های شناخته‌شده را رنگ می‌کند. هر چیز دیگری
خاکستری است. حدس‌زدن موفقیت از روی یک وضعیت ناشناخته، از گفتن «نمی‌دانم»
خطرناک‌تر است.

## ساختار کد (۳۲ کلاس)

| بسته | مسئولیت |
|---|---|
| `config` | خواندن `config.yaml` — «چطور بخوان» |
| `labels` | خواندن `config.json` — «چطور نشان بده» + زنجیرهٔ ترجمه |
| `flow` | ساخت گراف جریان از `commandList` |
| `parse` | مسیرها، تبدیل نوع، تخت‌کردن سند |
| `mongo` | اتصال، نگهبان فقط-خواندن، دروازهٔ داده، شمارندهٔ پرس‌وجو |
| `service` | یافتن لاگ، جستجوی پیشرفته، ترجمهٔ خطای Mongo به فارسی |
| `api` | دو کنترلر REST |
| `mask` | حذف/ماسک دادهٔ حساس با پروفایل قابل تنظیم |

**دو فایل پیکربندی، دو مسئولیت متفاوت:**

```
config/config.yaml   →  اتصال، فیلد زمان، مسیرها، محدودیت‌ها، قواعد ماسک
config/config.json   →  برچسب فارسی، گراف، فیلدهای جستجو، پروفایل حریم خصوصی
```

تیم عملیات معمولاً فقط با فایل دوم کار دارد.

## API — ده مسیر، و همین

| مسیر | کار |
|---|---|
| `GET /api/v1/log/{id}` | یافتن و آماده‌سازی یک لاگ — **یک** پرس‌وجو |
| `GET /api/v1/log/search/fields` | فیلدهای مجاز جستجوی عادی (برای ساخت UI) |
| `GET /api/v1/log/advanced/config` | عملگرها، فیلدهای پیشنهادی، متن هشدار |
| `POST /api/v1/log/advanced` | جستجوی سنگین روی فیلدهای بدون ایندکس |
| `GET /api/v1/meta/ui` | رنگ‌ها، چیدمان و شمار برچسب‌ها |
| `GET /api/v1/meta/health` | اتصال، وضعیت فقط-خواندن، ایندکس‌ها |
| `POST /api/v1/meta/config/reload` | بازخوانی هر دو فایل بدون ری‌استارت |
| `POST /api/v1/meta/indexes/inspect` | راستی‌آزمایی ادعای ایندکس |

هیچ endpointی برای فهرست، آمار یا نمودار وجود ندارد — نه غیرفعال، بلکه
**ناموجود**. `LogCollection` هم متد `aggregate` و `count` ندارد، پس
اجرای‌شان یک خطای کامپایل است، نه یک تصمیم زمان اجرا.

## مرزهای صریح

صادقانه بگوییم این طراحی چه چیزی نیست:

- **جستجوی متنی سریع ندارد.** جستجوی پیشرفته کند است و همین را می‌گوید.
  اگر جستجوی متنی سریع لازم شد، جایش ELK است — که همین حالا دارید.
- **تاریخچه و روند نشان نمی‌دهد.** یک لاگ، یک لحظه. روند کار Grafana است.
- **مدت هر مرحله را حساب نمی‌کند**، چون `commandList[].endDate` در دادهٔ
  واقعی وجود ندارد. اگر روزی اضافه شد، یک سطر config کافی است.
- **نتایج جستجوی پیشرفته مرتب نیستند** و این عمدی است.
